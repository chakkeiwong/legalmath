# Preserve declared holder, account and event identities

The remaining second admission of `entitlement` addresses a reproduced input
validation error, within its original financial-consumer scope. A debug-only
call using the retained Shell source accepted JSON holder IDs `true` and `1`
and merged their GBP60,000 and GBP40,000 holdings into one transfer. Python
dictionary equality caused the merge. The result was CONDITIONAL with no
unresolved premise. Source citations and correct coupon arithmetic do not
validate those holder identities.

## Evidence contract and intent

Question: can the current direct and selected coupon consumers preserve every
valid declared identity and reject malformed identities before aggregation?
Baseline: freeze the current pre-edit methods and actual P5/final-consumer
outputs for both retained Shell v3 forms and the selected v4 terms. Reuse the
sealed P1-P4 products explicitly; this is no fresh extraction or legal review.
Retain the original v2 identity-collision reproduction as well.

Primary pass criterion: exact equality of valid pre/post P5 question values and
final answers, including amounts, events, evidence, source identities and
Q1-Q6. Distinct string IDs such as `true` and `1` remain distinct; accounts for
one string holder still aggregate. Empty/blank and non-string holder, account
and event identifiers must reject before hashing or sorting. The direct route
must return typed UNSUPPORTED; selected terms retain their existing ValueError
refusal boundary. No input coercion, case folding or whitespace normalization.

Vetoes: an accepted malformed identifier, changed valid payment or source
evidence, hidden account, lost conditional qualification, source/method drift,
or unavailable required comparison. These are repair triggers for at most one
diagnosed changed repair, not permission for unchanged retries. Test totals and
runtime are explanatory only. Passing establishes finite engineering behavior;
it does not establish legal entitlement, actual note form, clearing, settlement,
independent source interpretation or general financial-engine completeness.

## Audit and assumptions

The first idea of merely adding more entitlement flags was rejected: the first
attempt already tests them. The new case discriminates a concrete untested
identity collision. Text IDs are a reviewed engineering requirement: JSON has
distinct number/Boolean types while Python keys can collapse them; nonblank
strings provide stable identities without interpreting client rights. Existing
string identities and exact arithmetic remain the baseline. Test this earliest
with the actual financial consumer, then preserve direct and selected forms.

The principal, flags, note form and events remain hypothetical development
inputs. The original source/form interpretation can still be wrong despite a
passing numerical comparison. Current P5 and final consumption are the actual
downstream target; isolated kernel tests alone cannot promote the repair.
Frozen P1-P4 reuse is explicit and cannot prove current intake or independent
construction. Methods and original PDFs must stay byte-identical during each
stage. Skeptical audit PASS with these limits; no numerical default changes,
package claim, provider call, installation or external message is needed.
