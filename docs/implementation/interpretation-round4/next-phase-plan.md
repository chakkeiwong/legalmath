## C2: institution staging

The local adapter and executable Java-host package exist. The bank must supply:

- A staging Java host/JDK, deployment location and service identity.
- Its actual control registry schema and fact mappings, including owners for facts
  requiring business or legal judgment.
- An operations-owned scheduler, source-update cadence, time policy and failure
  alert destination. No alerts may be sent until authorized.
- Release-role configuration and the institution's authorized activation process.

After these inputs exist, map the registry to the strict scheduler schema, retain
the exact configuration, run a read-only staged control evaluation, and exercise
a source update with the bank's actual fact snapshot. Compare typed Java outputs,
source and fact hashes, preserved prior revision, unaffected controls, timeout,
retry exhaustion and rollback/activation behavior under that environment. Use
institution release authority; a monitor result cannot approve itself. The local
fixture package is a reviewable integration example, not a production policy.

## Source and research limitations to carry forward

Historical FAQ applicability, unacquired statutory definitions and unsupported
visual text remain explicit dependencies. Component grouping and factor materiality
remain proposed interpretations. The argument/example profile is bounded; it is
not a full implementation of every surveyed legal-reasoning paper. Extend those
profiles only under a new source/method contract with discriminating negative
cases. Existing unresolved controls must remain unresolved in any successor Java
or monitoring package until their particular evidence gaps are addressed.

The stopping conditions are external evidence/budget and institution inputs.
Software uncertainty is not permission to hide a failure or silently replace a
control. See `method-boundaries.md`, the phase result notes and the execution report
for what has actually been implemented and tested.
