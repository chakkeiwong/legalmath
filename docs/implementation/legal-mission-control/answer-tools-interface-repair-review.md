# Review of the observed interface recovery

The first focused trial completed all eligible independent arms and charged
eight calls, for a final 25-call prefix. All four answers were rejected by the
declared output interface. The graph had 13 actual reference errors and separate
source/conclusion problems. The review supports one bounded recovery of those
failures, not a new unbounded series of plans.

The reusable answer_interface module places exact supplied facts, case IDs,
obligation IDs and delivered check keys into the provider schema. It fixes the
baseline tool-account length at zero. The consumer independently checks exact
case/fact pairing, P11 applicability, coverage and answer quotes. The module
replaces leaf schema dictionaries rather than modifying shared aliases; the
regression test confirms that ordinary answer prose remains unconstrained and
the original schema is unchanged. This avoids turning a metadata fix into a
restriction on legal reasoning.

The recovery runner preserves all predecessor files and begins from the final
25-entry ledger. It makes at most 17 additional calls (maximum aggregate 42):
one diagnostic-guided graph repair and eight independent answer/review pairs.
The actual graph-repair request is 122,920 bytes and baseline request 83,479
bytes, within the unchanged 200,000-byte cap. Later actual requests are measured
before dispatch, without truncating evidence. The original deadline, validated
300-second Settings, CPU-only policy and no-retry rule remain. At the review
time (12 October 2026 00:02:20 UTC), more than four hours remain;
17 calls reserve 5,185 seconds plus 600
seconds of review margin. Actual answer times and output sizes are unqualified.

The graph repair receives the actual failed output and all 13 diagnostics plus
the full source and generated readings. A successful syntax check cannot decide
its legal warrant: executor input review must inspect conclusion signs, P11/UT
identity, ordinary premises, assumptions and attacks. No automatic correction
or invented formalization is used to make the tool checks succeed. Both failed
readers remain excluded and all arms share that limitation.

The five focused new controls and eight predecessor controls passed. They cover
the actual metadata failure, unknown tool keys, unconstrained prose, case-pair
identity, unsupported P11 assumptions, complete graph diagnostics, byte limits,
and independent continuation after graph or answer failure. These are engineering
checks. The fresh baseline, source-reviewed legal criteria and actual delivered
checks govern assessment; one answer per arm cannot support a statistical ranking.

The new graph preserves all 21 prior tasks and attempts and adds one engineering
recovery, one finite live task, and its completion-only assessment. The engineering
attempt increases the cumulative count; it is not reset by the new version.
The old full-route live guard is untouched. The rule file exposes only fixed
recovery actions and grants no arbitrary shell or Python interpreter access.
Host installation and execution are separate commands requiring host approval
where the sandbox requires it.

Decision: PASS for this one bounded recovery, once the versioned program is
registered, the exact code/source/rule/ledger admission is retained and the live
task is reserved. A failure rejects this candidate and triggers its assessment;
it does not automatically authorize a second recovery. All original questions,
46 obligations, 35 readings and broader selected-tool evaluations remain open.
