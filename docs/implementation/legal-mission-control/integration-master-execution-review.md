# Execution review of the integration master

13 October 2026. This record supplements, and does not replace, the registered
master and completion contract. Historical attempts, 41 charged service calls,
18 prior detours and the one consolidated current revision remain unchanged.

The resumed skeptical review found material implementation gaps: the live action
was a placeholder; campaign preparation had been labelled a completed local node
without a counted proposal; requirement-detail failures could cancel independent
questions; final reviewer capacity had not been reserved against maximum output;
and copying existing legal notes did not complete the specified source research.
Those results remain preparation evidence, not acceptance evidence.

The correction stays within the current consolidated revision. First repair
local failure handling, exact resume identity, source and requirement coverage,
and the full product rehearsal. Then prepare a finite staged campaign with
explicitly counted acquisition, common preparation, baseline/candidate answers,
source and requirement reviews, interactions and comparisons. The approved
ceiling must include the entire declared workload; actual output-dependent
populations must be checked before descendants. A refusal preserves partial
work and does not authorize extra calls. Failed candidates do not block other
tools, questions or source research. A comparison needs a valid baseline.

The same inputs and common model checkpoints feed every matched arm. Retrieval
used to prepare common source packets is shared infrastructure, so the BM25 arm
tests the additional native retrieval feedback, not the claim that a baseline
has no retrieval. Null formalizations and unwarranted graphs remain unsupported.
Tool effects require fresh retained source-backed assessments; scripted checks
cannot establish those effects or legal correctness.

Source work must preserve exact original bytes and independently inspect the
rendering/extraction limitations. Dated public-source research and the private
facts requested are separate outstanding work. A source hash check alone cannot
close either. The program must name the work still required after preparation.

The seven-day local scheduling window was a convenience choice made at
registration to bound offline execution. It grants no service time, does not
extend historical authority and is not a prediction of task duration. Its
expiry pauses eligible dispatch pending reviewed continuation; it cannot erase
unfinished work. Each registered node retains its original two-attempt ceiling.

The saved `before/` files were captured after initial development began. They
protect the registration state, not an exact pre-task source baseline. Git and
the retained earlier artifacts supply additional history; unrelated dirty work
must remain intact.

Audit verdict: proceed with the bounded local correction and independent source
work. Live dispatch remains blocked until the executable campaign, measured
proposal, full-route tests, and concrete user approval are present. No broader
legal or tool-effect conclusion follows from this audit.

## Concrete execution supplement

The fixed `approve-and-run` action is the single grouped approval action. It
installs the named narrow rule file, attempts installation of the missing
`libreoffice-writer` component without an interactive password prompt, records
the explicitly approved grant, and starts the prepared campaign. Ordinary
resumption uses exactly:

```
.venv-context/bin/python scripts/legal_integration_master.py live
```

The requested service scope is **8,100 calls at most over six days**, starting
only upon approval, using the previously user-requested `gpt-6.1-sol` on the
existing configured provider route. Every call has a 120-second timeout, a
12,000-local-token / 200,000-byte visible input limit, and a
3,000-local-token / 24,000-byte output limit. These are reviewed finite trial
bounds, not proof of a model context size. The local tokenizer does not measure
hidden service framing or reasoning tokens. The package installation simulation
requires 11 new packages, a 16.0 MB download and 59.5 MB installed space.

| Stage | Maximum calls | Dependency and stop rule |
| --- | ---: | --- |
| Four source/reviewer canaries | 8 | Each question needs its own validated pair; an unsupported compliance control must not be accepted |
| Complete acquisition | 159 | Two readers, full original metadata/requirements and explicit bridges; failures remain charged and scoped to affected questions |
| Common preparation | 1,280 | Four independent caps of 320; check actual finding populations first, then persist details, reductions and common candidate/argument checkpoints |
| Baseline plus six arms for each question | 6,377 | Caps 268/187/269/187 for P10/P14/evidence/Gatecoin, seven arms each; actual detailed accounts plus maximum final output must fit reviewers before dispatch |
| Matched assessments | 144 | Six per comparison, 24 comparisons; baseline validity needed only for comparison |
| Cross-question assessments | 42 | Six question pairs in each of seven arms |
| Total declared stage caps | **8,010** | Global ceiling 8,100 does not authorize new stages or silent retries |

At the timeout bound, serial acquisition/canaries plus two parallel ready
workers fit inside six days with recorded headroom. Actual capacity can still
fail: generated findings may not contract sufficiently, an atomic supported
detail may be too large, a provider may reject its schema, or the native adapter
may have no warranted supported target. Those are retained branch outcomes;
they do not become legal impossibility findings. Clock and call ceilings both
apply. The lower-bound acquisition screen is explicitly a refusal screen, not
proof of fit. The actual request and downstream reservation checks remain
mandatory.

The common preparation is separate from the baseline answer. Candidates can
therefore proceed when the baseline answer or its review fails. Every candidate
still enters the complete public product route and revalidates its shared
source/checkpoint identities. The comparison holds model, questions, source
access and common generated premises constant. Native feedback is the intended
arm difference. Each independent service worker owns its own provider instance;
the shared allowance and supervisor use file locks. Restart reuses completed
identical requests. A live node with a dead supervisor resumes its existing
attempt; unknown reserved requests block redispatch.

The program deliberately does not turn an automated closeout into substantive
acceptance. `release-review` retains separate decisions and requires the agent
to inspect actual source warrants, adverse cases, all original handling records
and the seven integration stages. A comparison that is missing a supported
target remains insufficient. Final acceptance and corpus research are explicit
agent deliverables in the same program; no new successor program is implied.

The official Codex rules page could not be fetched (HTTP 403). The installed
CLI's `execpolicy check` confirmed the exact `live` and `verify` forms match
the prepared rules; arbitrary `python -c` and `approve-and-run` do not. Approval
of `approve-and-run` must be explicit. Host rules cannot renew grants or promise
that the host will never request permission.
