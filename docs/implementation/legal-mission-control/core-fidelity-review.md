## Question and evidence contract

Does the **actual core** `semantics.fidelity_request` fit the unchanged
200,000-byte input cap on the labeled hybrid fixture, and what does its
preflight require before the existing 23-call baseline-core remainder could
cover later work? Comparator: the current 32-pair core setting, 200,000-byte
input/output caps, 2 MiB aggregate fidelity limit and 36-call core allocation
of which thirteen have been charged. A 64-pair core setting is a policy
hypothesis, not a new default. Preserve all 55 qualified source units, all 67
non-CONTEXT claims of the actual partial inventory, and all twelve historical
candidate readings. Remap historical quotations only when exact occurrence is
unique. Classify candidate compilability through the same `bundle` check used
by the core stage; do not call Java, a provider or a GPU.

The primary engineering screen is full assigned-pair conservation and every
prepared encoded input within 200,000 bytes. A changed source/hash, lost pair,
bad qualification or failed exact reconstruction vetoes this diagnostic. The
preflight call and byte arithmetic are conditional capacity evidence. Actual
responses, their aggregate byte volume, latency, semantic fidelity and final
answer quality are **unmeasured**; passing the input screen cannot promote the
method. Retain the exact artifact, script/plan/input hashes, CPU-only environment,
wall time, candidate classifications and counts. No result changes the
immutable call grant or stage allocations.

Construction uses `2026-10-10T00:00:00.000000Z`, validated through the current
timestamp parser. This is a valid fixture date for the bundle identity, not a
claim about which law governs at that time. Schema/date failures must not be
mistaken for unsupported legal readings.

The earlier continuation summary described the core constructor as supplying
all claims and candidates in every batch. Direct inspection of

filters both lists to the batch IDs. This measurement uses that actual
