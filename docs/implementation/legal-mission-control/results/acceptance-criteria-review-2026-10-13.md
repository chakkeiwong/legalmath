# Acceptance criteria: origin, proportionality and proposed corrections

13 October 2026. Review requested by the user: are the original acceptance
criteria reasonable, are they overly stringent, and how were they established?
This is an assessment of the retained plans and current controller. It changes
no acceptance requirement, task, evidence hash, grant, allowance or disposition.

## Verdict

The core requirements are reasonable for the claimed capability: answer the
actual question, preserve materially different interpretations, support claims
with correctly attributed sources, keep unknown facts explicit, and demonstrate
that an enabled tool actually reaches the answer. Source-supported conditional
answers and valid negative tool findings are already permitted. General English
perfection, universal legal certainty and a positive effect from every package
were not the original acceptance target.

Some accumulated workflow requirements are stronger than their justification.
The implementation also blurs evaluation completion with integration and uses
a blanket tool/question matrix. These choices can prolong execution without
equivalent evidence of product quality. Relaxing them would not cure the known
citation, source, capacity or missing-answer defects.

It permits conditional answers and unchanged/harmful trial results; a large matrix is explicitly unnecessary before the first complete case. |

Finite tests cannot establish general English correctness. |

The master itself calls the readers and capacity limits inherited or unqualified choices. They are not external standards. |

The user's repeated instructions supplied the objectives: thorough integration,
actual product progress, reviewed plans and no drift toward easier tasks. The
detailed acceptance mechanics were specified in the project plans and code.
The inspected record does not establish that each mechanic was separately
chosen by the user, validated as cost-effective, or prescribed by an external
benchmark or legal authority. Authorization to execute the program is not
evidence that its experimental design was optimal.

The lineage is supported by retained dated documents and inventories. Several
later files are untracked in the current worktree; git history does not provide
a complete independent authorship/edit chronology for them.

## What should remain and what should change

| Requirement | Assessment | Proposed treatment |
| --- | --- | --- |
| Correct source identity, quotations and proposition attribution | Necessary for accepting an answer as source-supported | Retain. A known material false citation or lost decisive exception rejects the affected answer. Rejecting a bad answer does not invalidate unrelated work or automatically prove tool harm. |
| Preserve the original question and material alternatives | Necessary | Retain. A duty-trigger calculation must not substitute for fulfillment; uncertainty and conditional alternatives can be correct outputs. |
| Preserve 46/35 original identities | Reasonable for traceability; excessive if interpreted as proving every generated request separately | Keep a complete disposition map. Allow reviewed duplicate, irrelevant, unsupported-demand and external-fact classifications while retaining original IDs and reasons. Coverage does not require one live call per item or automatic formalization. |
| Test actual integration and downstream use | Necessary for claiming the selected path is integrated | Retain an actual product test. A component check supports a narrower milestone; an alternative product path requires explicit scope review rather than a silently substituted pilot. |
| Run all six tools on all four questions | Not justified as a universal execution requirement | Predeclare applicability. Every pairing receives a reasoned disposition, but live trials target supported mechanisms and nonredundant failure cases. Do not reject a tool merely because one unrelated question is unsupported. |
| Two same-model readers plus repeated full-source reviews | A testable method choice, not established assurance | Retain source access and demonstrated coverage. Assess the incremental value of repeated passes; permit reusable verified source work and focused interaction/counterexample review where equivalence is justified. Model agreement is not independent legal validation. |
| Matched answers for a tool-effect claim | Reasonable | Require a valid comparison to claim benefit, harm or no observed benefit. A reviewed scope rejection can conclude applicability without pretending a nonexistent supported comparison ran. |
| Proof of unique natural-language meaning | Appropriate only for an explicit formal-proof claim; excessive as a requirement for useful conditional assistance | Accept defensible source-reviewed analysis with uncertainty for the declared use. Expert review supplies practical assessment evidence, not proof of universal truth. Stronger deployment/generalization claims need their own evidence. |
| Fixed timeout, token limits and attempt caps | Operational bounds, not legal-quality standards | Measure and justify them for the complete route. Capacity failure is not a wrong legal interpretation; never reset historical consumption to adjust a future policy. |

“Material” needs an explicit rubric before tests: for example, an attribution or
omission that changes the conclusion, applicable condition, supported alternative
or required factual dependency. This review sets no invented error-rate threshold.
The current control cases remain development evidence; broad accuracy or
deployment claims need independent cases, domain review and a justified
reliability design appropriate to the intended use.

## Concrete mismatch in the current implementation

`scripts/legal_mission_control.py::status` computes the field named
`selected_tools_fully_evaluated` by summing `fully_integrated`. Its mission-ready
condition also requires every currently selected tool to be fully integrated.
The validator permits reviewed disposition changes, so it does not literally
make rejection impossible. However, there is no separate evaluated-and-rejected
completion counter. The displayed quantity conflates two different decisions
that the 12 October contract explicitly separates. Correcting that reporting
model must not manufacture new evaluations: the current audit still reports
missing complete original-answer comparisons.

`scripts/legal_integration_master.py::prepare` constructs tool and comparison
nodes for each member of QUESTIONS crossed with each member of TOOLS. That is
24 tool-answer branches and 24 comparison branches before an explicit
per-pair applicability filter. The graph can retain those rows for accounting,
but a justified not-applicable or reviewed rejection route should not require
an irrelevant live experiment. This is a design review finding, not evidence
that the 24 branches already executed or caused the latest preflight failures.

The older instruction that “No human answer labels ... will qualify a
natural-language interpretation” concerns proof of source meaning. Applying it
as a prohibition on domain-expert evaluation for a scoped assistive product
would remove a useful practical acceptance method. The proof claim and the
fit-for-purpose evaluation must be distinguished explicitly.

## Recommended acceptance structure

1. Engineering qualification for a declared entry point, source profile and
   supported tool configuration: real invocation, identity, error handling,
   resume behavior and complete-path capacity.
2. Evaluation disposition for every selected tool: applicable and evaluated,
   evidence-backed rejection, limited supported scope, or incomplete evidence.
   Only the first three can close the scoped evaluation decision; none implies
   successful deployment merely by being recorded.
3. Original-question handling: a reviewed answer with material sources and
   alternatives, plus a complete disposition map for historical records.
   Missing facts and unresolved law can remain explicit conditions.
4. Broader release or reliability assessment only for the intended deployment
   claim: independent examples and domain review, declared severity and
   performance criteria, and uncertainty evidence where generalization is claimed.

These are separate milestones within the existing program, not a replacement
population or a new permission grant. Historical failures remain. Any actual
change should preserve the old contract, map every old criterion to retained,
reclassified or replaced evidence, review the implementation of that map, and
state exactly which completion claim becomes available. No historical failure
can be retroactively reported as a pass under a changed criterion.

## Skeptical review

The strongest risk in this proposal is lowering the standard merely to obtain
a green status. Prevent that by retaining source accuracy, question fidelity,
material distinctions, actual integration and supported scope, with no invented
new success. The opposite risk is treating every generated concern and every
inherited workflow setting as a permanent product requirement. Explicit
criterion provenance and per-item dispositions address that risk.

The review supports reclassifying procedural choices and correcting reporting,
not declaring the unfinished integration acceptable. We have not measured that
a cheaper review procedure is equally effective. The frozen original questions
are suitable development cases; they are insufficient alone for a general
accuracy claim. No benchmark, live call, repair or acceptance migration was
executed as part of this review.
