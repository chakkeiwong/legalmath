# Integration failures: supported limitations and a finite resolution

13 October 2026. This review supplements the existing integration master and
its [executed audit](integration-master-audit-execution-2026-10-13.md). It records
the distinction requested by the user between our unfinished work, limitations
of the current product, and questions that require external evidence or a legal
decision. It does not establish that the integration defects are impossible to
solve. No further live execution or attempt is admitted by this review.

The current conclusion is **integration incomplete**. The route has repairable
software defects and unfinished source work. Its preservation of meaning through
partitioned requests remains unqualified. The six selected tools have executed
native controls, but none has a complete evaluation of its effect on the
original answers. The correct response is to finish a defined supported scope
and report the residual limits, with a finite evaluation and an explicit exit.

## What the failures actually establish

The latest 57 calls comprised 49 semantic-control calls and eight canaries.
Both unpartitioned controls returned the expected consequence with operative
quotations. The partitioned remote-exception case timed out during reduction;
the changed-exception case encountered five HTTP 502 errors and one HTTP 503.
Gatecoin additionally exceeded the expanded-output limit, and its reviewer
disconnected. These outcomes establish failure of the tested execution to
complete. They do not establish semantic disagreement, useless tools, or
impossibility of decomposition. Conversely, service failures do not establish
that the missing partitioned answer would have been correct.

Two concrete implementation choices help explain the repeated stopping:

* `scripts/legal_integration_campaign.py::_live` calls `complete_node` for ready
  acquisition nodes when the shared semantic prerequisite fails, even though it
  explicitly records that acquisition was not dispatched. `complete_node`
  starts an attempt before writing that failure. Thus attempt 3 consumed all
  four acquisition attempts without testing those acquisitions. The historical
  counts remain valid records of the scheduler's actions, but they are not four
  additional failed original-answer experiments. Future accounting must separate
  prerequisite blockage, actual dispatch, candidate rejection and uncertain
  service outcome. This is an additional concrete R09 scheduler finding.
* `bounded_references.resolve` expands each short span reference into quoted
  text. The wire result and expanded result are both checked against the route's
  output-byte limit. Repeated evidence references can therefore overflow after
  a compact response arrives. Qualifying input fit alone misses this failure.
  This is a representation/capacity issue under R14, not evidence that the
  source document cannot be processed.

The program also reaches the substantive acceptance question too late. Native
execution, scripted rehearsals and 156 passing local regression tests answer
engineering questions. They cannot show that a package improved an original
legal answer that the campaign never completed. That explains why real local
repairs coexist with zero fully evaluated selected tools. The next evidence
must include complete source-supported answers and tool effects.

## A finite continuation with an honest exit

The recommended continuation is one consolidated repair package followed by a
defined qualification and original-answer matrix under this same master. Before
dispatch, its execution packet must derive a finite call/time/output budget from
the actual complete requests, retain the existing grant/deadline, and state any
explicit reviewed attempt change. Unused global calls are not a fourth attempt.
The current local code is newer than the consumed live binding; it needs its
own reviewed identity and qualification. No binding is changed by this note.

Source/legal work and local representation/scheduler/native work are independent
branches. Shared source or schema changes serialize at a reviewed input freeze.
The semantic test needs the relevant source/representation repairs to succeed.
Each original answer then needs only its own qualified sources/acquisition;
each tool arm needs its own warranted supported target. Comparisons need both
valid arms. Delivery review depends on completion of all branches, including
failed or unsupported outcomes. Global authority, integrity and deadline vetoes
remain distinct from an ordinary branch failure.

Retries must answer a new discriminating question. A deterministic output
overflow triggers representation repair, not a repeat of the same request. A
source-supported semantic counterexample triggers its declared repair, not a
claim that the service is unavailable. A terminal transient service failure can
use only its predeclared transport allowance. A timeout/disconnect with an
uncertain dispatch outcome must be reconciled before replay; all reserved
charges stay retained. `SettledProviderFailure` already expresses that distinction
in `assurance/failure_policy.py`.

One source-backed answer correction is a proposed operational ceiling, not an
estimate that one retry will succeed. Its exact resource reservation belongs in
the continuation packet. Local editing/test iteration is not a new live-answer
attempt. The package ends when its required results exist or its declared bounds
are exhausted, after all independent authorized branches and declared recovery
have completed. Failure at that point produces a dated incomplete/unvalidated
scope with an owner and evidence needed to reopen. Reopening requires a concrete
changed cause or scope decision; it is not automatic after another failure.

The final deliverable needs three separate decisions, as the existing
[completion contract](../../../plans/legal-mission-integration-completion-contract-2026-10-12.md)
already requires: engineering qualified for its declared configuration; each
selected tool's applicability/contribution evaluated; and each legal question
answered conditionally, substantively unresolved, or awaiting specific external
evidence. A justified rejected tool can finish its evaluation without becoming
an integrated production dependency. Unsupported adapters retain their exact
scope. Four questions, 46 obligations, 35 readings, 12 cases, 224 premise records,
407 subparts and all 26 surveyed-tool dispositions remain visible.

## Skeptical review and record-update decision

The baseline is the actual third-attempt state, not the scripted rehearsal or a
fresh graph. The evidence supports implementation defects, observed service
failures and adapter restrictions. It does not support a semantic success rate,
a tool ranking or a general impossibility result. A competing explanation is
that semantic defects will remain after service repair; a complete paired answer
with original-source review is needed to discriminate it. The weakest evidence
is still actual meaning preservation and downstream tool contribution.

The 120-second timeout, 12,000/3,000 local token limits and hidden service framing
remain unqualified settings. The first comparator's 2,180 local tokens versus
13,832 provider input tokens does not isolate framing from tokenizer effects.
Adapter size bounds are verified implementation limits, not measured limits of
the underlying packages. The proposed correction ceiling controls spending; it
is not a scientific default or evidence of sufficient reliability.
