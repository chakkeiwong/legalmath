# Next implementation round: providers and independent evaluation

This plan follows the executed E01–E09 engineering increment. Its baseline is the
final accepted code and evidence identified in [execution-report.md](execution-report.md).
The next question is whether independently proposed readings and targeted repairs
improve detection of consequential interpretation errors on unseen source material.
The present scripted-member tests cannot answer it.

## Preserve the boundaries established this round

The next implementation must preserve source inventory independence, immutable
initial outputs, explicit hypothesis families, no-refund action accounting,
complete unresolved reports and exact evidence binding at release. A live adapter
may propose claims and actions; it may not supply reviewer authority or mark checks
passed. A solver comparison concerns encoded behavior within its declared domain.
A repaired reference does not establish repaired meaning.

The current browser supports investigation, inspection and meaning decisions. The
API also supports inventory review, issue adjudication, cancellation and explicit
successors. The fixture provider accepts pre-authored proposals and repairs. Its
lexicographic scheduler, finite caps and shared-process recovery are baselines.
The largest untested failure remains common misunderstanding across all proposed
readings and all same-author tests.

No values are inferred from the fixture's four-member, twelve-action policy.

## Repair and plan refresh after every phase

Retain the current supervisor pattern: fixed command registry; narrow exact command
prefix; immutable attempts; pre-run review tied to code and plan hashes; finite
subprocess limits; counted failures; actual repair notes; refreshed successor plan.
A failed candidate is not evidence to stop the research direction when a later
phase explicitly tests a repair. Corrupted evidence, invalid comparators, unauthorized
costs or exhausted approved budgets do stop dependent execution.

Each refresh must state what the completed phase established, what failed, the
implemented repair, unresolved uncertainty, affected acceptance criteria and the
smallest next discriminating check. Do not carry a favorable descriptive result
forward as an approved default. A live-model run needs an intent ledger separating
promotion criteria, promotion vetoes, continuation vetoes, repair triggers and
explanatory diagnostics. A pass requires the declared downstream legal-error
criterion, not model agreement or a high priority score.

A before/after example should accompany every consequential repair: the retained
passage; initial rival readings; omitted assumption or route; affected facts;
corrected candidate; changed decision/witness; what the formal test established;
and the human issue that remains. This round's product-type omission is the
engineering template, while its same-author oracle remains an explicit limitation.

## Defaults and decisions still open

| Choice | Current status | Failure mode and earliest check |
|---|---|---|
| Model/provider diversity | Unselected hypothesis | Shared errors may survive unanimity; inspect independently annotated common omissions. |
| Number of members/actions | Fixture convenience only | Excessive agreement or premature blocking; measure downstream error and abstention under equal budgets. |
| Corpus size and split | Not chosen | Circular-family leakage or insufficient consequential cases; freeze the sampling/split protocol before candidate runs. |
| Risk score or confidence probability | Not implemented | Numerical confidence could obscure semantic uncertainty; retain explicit hypotheses and calibrate only against independent held-out adjudication. |
| Tree-search strategy | Optional research candidate | More search may amplify shared assumptions; require a fair deterministic-baseline comparison. |
| Enterprise approval authority | Local synthetic registry only | Local credentials could be mistaken for legal authorization; bank identity and authority tests precede any shadow deployment. |

The next agent should begin with N0/N1 and the independent annotation tooling,
then pause only at the concrete provider-spend and human-annotation boundaries.
The successful engineering increment is a starting platform for that evaluation,
not evidence that autonomous English-to-code translation is safe for the bank.
