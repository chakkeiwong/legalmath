# Restorable application and installed consumer check

Question: can the repaired service build and assess new inputs from a fresh,
non-editable installation, with no checkout imports, and do the same after its
source/resource directory is moved? This is R6 of the integration closure plan.

Resumed-run audit: extend the original three controls to eight cases, adding
calculation-amount rounding and schedule dates, cross-document exception,
AST reference mapping, thirteen-fact Z3 construction/law, and the source-bound
Compass conditional first coupon. Compass retains the three original PDFs,
EUR3,500 expected payment and nine anniversary dates, with Q3 still PARTIAL.
Its family is development-exposed. These inputs are constructed or copied before
the isolated command; P1–P5 are built by the installed service. The latest source
method is captured before building and must remain unchanged during execution.

Comparator: current checkout service results on frozen development repayment,
authored-exception and selected-coupon inputs. Exact question payloads and source
hashes must agree; the explicitly different assessment/replay mode and absolute
input-root names are not comparison targets. The installed process must itself
build P1–P5 and run the public `legalmath prospectus assess` command. Import paths
must point to the new environment. Source and rate mutations must reject.

Prepare a wheelhouse under `.localresources/prospectus/closure-runtime/` using
versions already installed in the application and optional CPU environments.
Bind every wheel with SHA-256 and generate transitive requirements with hashes.
Install the application and its dependencies into a new venv without system
site packages. Do not use `--no-deps` as proof of clean installation. Restoration
uses the complete locked wheelhouse with network disabled. Remove one temporary
runtime directory and restore it again; an old receipt cannot replace missing
runtime files. Preserve the build inputs and hashes in a new closure attempt.

Initial resource budget: 600 seconds per subprocess, 20 minutes total,
1 GB downloaded wheels, 3 GB temporary environments and outputs. Core plus
Cassis/QuantLib/PyMuPDF profiles are expected below these bounds. Docling model,
Java server and browser restoration are separately pending until their exact
package/model inventories and larger budgets are recorded. No GPU import or
training-environment mutation is authorized by this action. Child environments
set `CUDA_VISIBLE_DEVICES=-1`, `PYTHONNOUSERSITE=1`, and remove `PYTHONPATH`.

Promotion veto: wrong supported answer, checkout import, absent dependency,
unexplained comparator mismatch, unbound wheel, or input mutation accepted.
Continuation veto: invalid input/comparator, resource bound exceeded, missing
diagnostics or unintended historical write. Failures trigger a corrected
manifest/implementation and new attempt. Timing and package counts are
explanatory. A passing result proves this recorded host/interpreter profile,
not operating-system portability, source interpretation, independent legal
acceptance, or native-read confinement.

Skeptical review: PASS after checking that the current `.venv` is a distinct
application environment even though its base interpreter lives in `tfgpu`.
Building in a copied staging tree avoids accidental imports and egg-info edits
in the checkout. Dependencies come from the installed-version baseline, whose
appropriateness remains bounded to the development cases; successful imports
alone cannot satisfy the service criterion. Absolute fixture paths must be
rewritten before freezing expected reports so relocation is a genuine test.

Artifacts: new `installed/attempt-NNN/` directories under the closure namespace,
with command logs, lock hashes, wheel/source hashes, interpreter metadata,
method identity, requests, reports, comparison result and restoration records.
Fixed command: `python3 -m scripts.prospectus_closure_install application`.
