# Tool reuse and legal interpretation: finite comparison program

Date: 6 October 2026. User authorization: create, review, prepare the command allowlist,
and execute the tool-first comparison proposed in this conversation.
This program is a new bounded investigation, not an appended S5 phase.

## Problem and governing question

The product can execute declared interpretations and preserve uncertainty. The
completed follow-up leaves 46 obligations OPEN_QUALIFIED, preserves 35 readings
and 70 role references, and records 32 unformalized readings. It has not justified
the relation from source language to governing fulfillment standards, observations
to normative judgments, or precedents to the target arrangement.

The question is whether available external tools contribute a demonstrable
capability on these specific problems before further bespoke reasoning is built.
A tool's installation, agreement, extra citations, extra readings, successful
compilation or internally consistent argument graph is not substantive closure.

## Baselines and comparison units

Freeze the selected S4 result and the problem-led follow-up result, their plan and
final decision, the obligation/premise/question registers, source packet, and
retained case dossiers. Preserve original wording and hashes. The scripted S4
run is the engineering baseline only; it is not a live interpretation comparator.

The live comparator uses the same existing CompleteInvestigation implementation,
same dated retained public sources, same original questions, same configured
provider/model route, same per-arm limits and same default semantics. Its paired
candidate receives separately identified external-tool results. Source availability
is equal: retrieval reorganizes an identical corpus and adds no hidden answer key.
Run baseline before candidate as a declared convenience; with one run per arm,
order, model sampling and prompt differences prevent a causal accuracy ranking.

Four target questions are fixed before trials:
- Paragraph 10: what standard supports responsibility or fulfillment, and what
  follows separately from delegation, retained authority, conduct and outcomes?
- Paragraph 14/footnote 5: how do trigger, object and standard attach, including a
  missing SFC request?
- Evidence: what additional standard connects an observed supervision or
  reconciliation event to adequate supervision or proper records?
- Gatecoin: what source-supported distinctions concerning terms, consent,
  actors and relationships bear on a target ownership inference, and what
  applicability and later-treatment premises remain missing?

These are development questions derived from existing dossiers, not held-out
legal answer labels. Freeze their full text in T0. Never substitute duty
applicability for fulfillment. No client facts or new legal corpus are invented.

## Evidence contract and research intent ledger

| Item | Declared role and decision |
|---|---|
| Main mechanism | External representation, retrieval and argument engines may expose information loss or unsupported inferences in the existing route. |
| Expected failures | Incomplete archives; unsupported Hong Kong citations; mismatched argument semantics; controlled-language syntax mistaken for source understanding; rankings driven by authored examples. |
| Engineering pass | Actual pinned external engine runs through a bounded adapter; source/identity/unknown states are preserved; checked invariants and positive/negative controls pass. |
| Adoption criterion | A specified reusable capability is demonstrated on relevant inputs with inspectable evidence and acceptable integration scope. Adoption is limited to that capability. |
| Substantive criterion | A particular original obligation has a source-supported argument or checked relation resolving its named missing premise. Model assertions and tool agreement alone cannot meet this criterion. |
| Promotion veto | Lost source or question identity; unsupported passage attribution; unknown converted to false; silent priority/default; omitted alternatives; unbounded/incomplete run presented as complete. |
| Continuation veto | Corrupt frozen inputs, broken accounting, unauthorized action, unresolved harness error, or exhausted program budget. A failed tool blocks its adoption, not other independent trials. |
| Repair trigger | Reproducible adapter/API/environment defect. Preserve failure and apply a focused bounded repair; do not alter the legal target or success criterion. |
| Explanatory only | Counts, timings, retrieval ranks, token use, test totals, model agreement and newly proposed legal arguments. |
| Nonconclusions | General English fidelity, legal accuracy rate, statistical superiority, future-source generalization, client compliance, or production readiness. |

The small live comparison is descriptive. No stochastic ranking is supported.
If candidate output differs, inspect source support and alternative explanations;
retain both outputs. Formal checks answer declared computational questions only.

## Phases and refresh mechanism

T0 — Freeze baseline, sources, questions, code identities, run intent and budgets.
Check retained hashes and summarize the current capabilities. Artifact: baseline.json.

T1 — Acquire complete pinned candidate archives in a separate local resource
directory; preserve licences and hashes. Prepare isolated dependencies and local
Go/SWI runtimes only within the declared setup actions. Perform bounded import/API
checks and record unavailable/unsupported candidates without treating them as
negative legal findings. Artifact: acquisition.json and environment.json.

T2 — Execute external-engine component comparisons and adversarial controls.
Check matching semantics, citation jurisdiction coverage, actual parser/schema
availability and retrieval provenance. Retain raw inputs and outputs; repair
adapter failures within the cap. Artifact: components.json and per-tool logs.

T3 — Execute paired baseline and tool-assisted model trials, then actual
CompleteInvestigation workflow trials where useful adapters pass T2. Use source
and question parity; preserve provider requests/responses, allowance reservations,
tool context and actual computation receipts. Missing capacity or failed provider
calls produce incomplete evidence, not fabricated scripted replacements.
Artifact: live-comparison.json and product dossiers.

T4 — Audit all receipts and original obligations. Decide adopt/adapt/defer/reject
for every candidate, distinguish reusable capability from substantive closure,
record necessary residual custom work and finish. Artifact: result.json,
result.md, validation.json and reset memo. There is no automatic successor.

Before each phase the runner records a refreshed plan containing predecessor
result hash, observed failures, remaining budgets, exact phase action, question,
vetoes and decision scope. Completed phases are immutable and verified before reuse.
A failure remains in an attempt directory. Resume uses durable state; no call
refunds or silently reset budgets. No skipped phase can appear completed.

## Budgets, execution and approval policy

CPU only, CUDA_VISIBLE_DEVICES=-1 before scientific imports. No GPU, model training,
system package installation, external messages, publication, commit or push.

- At most 48 model calls, including failures and repairs, in a new program ledger.
- At most 12 explicitly recorded network acquisition/install processes; dependency
  managers may issue several HTTP requests within a recorded process.
- Download allowance: at most 512 MiB retained candidate archives/packages; reject
  oversized direct downloads and inspect dependency download size before installing.
- Four repair attempts for implementation/environment failures, each preserving
  rejected output; no automatic scientific criterion changes.
- Four-hour execution window starting at first execute; individual provider calls
  at most 300 seconds and external processes have explicit deadlines.
- Model selection inherits the existing configured route and records its identity;
  no model migration or statistical independence claim.

## Skeptical audit before implementation

PASS FOR BOUNDED IMPLEMENTATION, with the following repairs already incorporated:
1. The prior proposal could compare a live candidate with a scripted baseline.
   Both live arms now use the same provider and inputs; S4 is engineering history.
2. External solvers could silently import legal priorities or proof standards.
   Trials require matched declared semantics, or are labelled separate alternatives.
3. An easier duty question could replace the original fulfillment question.
   T0 freezes original questions and all 46 obligations; no closure through renaming.
4. A library installation or passed test could masquerade as a legal solution.
   Engineering adoption and substantive closure have separate criteria and reports.
5. Installing the full catalogue could exhaust effort without answering a gap.
   Each candidate has a bounded trial and terminal disposition; no endless phases.
6. A resource or network failure could reject the research direction.
   Such results are environment/under-budget findings; independent trials continue.

Pre-mortem: all checks may pass because the authored examples and model prompts
share an interpretation mistake. Checked source offsets do not prove that an
inference follows. A specific contrary passage, lost alternative, or mistaken
case-to-target inference overturns that candidate conclusion. Paired live results
are descriptive and require substantive inspection, not a score-based winner.

The runner returns after each phase for a supervisor review before the next exact
execute invocation. This does not request a new user approval. The runner and
adapters require a second implementation audit and targeted tests before setup/execute. T4 must include decision and inference-status tables, the
strongest alternative explanation, what would overturn each adoption claim, and
the weakest evidence.
