# Prospectus root-cause investigation

6 October 2026. Investigation and delivery-program design; implementation of the
new program is not part of this run.

## Question and evidence contract

Why have repeated source and reader repairs not produced a deliverable prospectus
service, and what complete, bounded program would change that?

The baseline is commit `da2c7a4336cbd1146a9d5b8896bc982d63668441` in
`feature/prospectus-evidence-master`. Trace the repository entrypoints and imported
reader, the frozen 4 October candidate, and the optional 5 October continuations
as separate implementations. Compare code with retained inputs, outcomes and
verification records. Git delivery is already complete. Historical uncommitted
statuses must not be mistaken for current gaps.

Pass criterion for this investigation: every proposed delivery phase addresses
an evidenced failure or an explicitly identified intended-use requirement, names
its executable deliverables and dependencies, and specifies an observable exit
test. Every material diagnosis needs code/evidence anchors or must be marked as
a hypothesis. The program must include actual reader integration, independent
evaluation, finite repair loops and human/source dependencies.

Invalid or mismatched source identities, wrong executable baseline and misleading
evaluation denominators veto a diagnosis until repaired. A failing candidate
does not veto the investigation. Test totals, source counts and formal checks
are explanatory diagnostics, not measures of legal accuracy or production
readiness. Do not estimate unseen accuracy from the exposed development corpus.

Artifacts: an investigation report, a technical literature review with exact
local sources, a phased delivery specification, a skeptical review and a reset
memo under a new 6 October directory. Preserve earlier receipt-bound evidence.

## Method

1. Trace acquisition, extraction, source selection, interpretation, classification,
   financial calculations, jurisdiction treatment and reporting. Follow imports;
   do not infer integration from file proximity.
2. Inspect representative failures in source and retained results. Use only small
   CPU diagnostics if static inspection cannot decide a material question. Retain
   their command, baseline, result and limits. No full corpus rerun is needed to
   rediscover documented outcomes.
3. Read relevant retained papers' technical methods, evaluation and applicable
   appendices. Inspect official code where retained. Use ResearchAssistant
   parsing when useful and available. Existing local sources come first; the
   retrieval ledger has 24 requests remaining if an essential source is missing.
4. Propose the smallest architecture that addresses the evidenced causes,
   including a product boundary, concrete interfaces, source and legal reasoning
   obligations, evaluation design and an executable phase controller.
5. Red-team the program and repair findings before presenting it. Validate links,
   dependency ordering and consistency with actual implementation status.

## Assumptions and audit before investigation

| Choice | Provenance and status | Failure risk | Early check |
| --- | --- | --- | --- |
| User seeks a delivery program before another implementation campaign | Latest request; reviewed scope assumption | Accidentally implement a large unreviewed redesign | Keep deliverables diagnostic and specify future commands explicitly |
| Current feature HEAD is the relevant baseline | Prior integration receipt; verify locally | Diagnose a stale or optional implementation as production | Check HEAD and trace imports from each entrypoint |
| Retained evidence can explain recurring failure mechanisms | Existing campaigns; working hypothesis | Summaries overstate what code does | Inspect code, source excerpts and raw result records |
| Existing literature is adequate to design an initial program | Retained technical sources; convenience choice | Miss a needed method or reuse an unsuitable benchmark | Inspect task definitions, limitations and official implementations |
| Bounded CPU probes suffice for diagnosis | No training or speed claim; reviewed default | Probe accidentally becomes claimed performance evidence | Label probes debugging-only and retain exact scope |

Skeptical audit: pass for investigation. The plan checks executable baselines,
does not promote proxy metrics, preserves unrelated work and historical receipts,
defines invalid-evidence stop conditions, and treats unavailable legal inputs as
delivery dependencies. There is no method ranking, training, GPU use or paid-model
run. New implementation commands will require a separate phase audit. Remaining
uncertainties concern the actual code paths and evidence, which the investigation
is designed to resolve.
