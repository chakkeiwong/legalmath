# Common capacity management for the legal integration master

The user requests a common capacity interface wired into every stage, adequate
tests, skeptical review, a refreshed master and execution. This is a revision
of the existing legal integration program, not a replacement of its legal
questions, acceptance criteria or evidence. The prospectus work is separate.

## Question, baseline and authority

Engineering question: can every current master request use one auditable
capacity contract, reuse completed work, and either produce a validated complete
result or identify the precise bounded remainder? The baseline is the current
candidate-capacity revision, its real requests, all retained failures and the
running supervisor. At initial inspection, 3,484 of 8,100 calls are charged;
the BM25 P14 owner is awaiting its recorded service replacement at 15:39:29 UTC.
Its old implementation must remain unchanged while it is running. The current
global live deadline remains 20 October 18:55:16 UTC. This request authorizes
implementation and bounded validation; it does not silently extend live time,
reset attempts, replace a service grant or erase the spent recovery reserve.

Scope is every stage of the current bounded master route: source reading,
source-dependency reading, metadata inventory, requirement accounts, synthesis,
candidate generation, criticism, native tools, answer construction, source and
requirement review, context bridges, warrant decisions, account/answer
correction, interaction review and matched tool-effect assessment. Historical
sealed runners remain evidence. Local native tools run on the validated complete
assembled input; their formal semantics must not be approximated by concatenating
independent solver results.

Primary acceptance: every current stage has an explicit registered adapter or
local atomic disposition; all model calls traverse common input/output budget,
identity, persistence and validation checks; exact sources and assignments are
preserved; cross-piece dependencies are checked; independent pieces continue
after ordinary failures; restart never repeats a completed or uncertain call.
Actual semantic controls, production-request replay and regression tests are
required. Test totals, fit measurements and invocation receipts do not establish
legal correctness, answer acceptance or tool benefit. Four original questions,
46 obligations and 35 readings remain mandatory.

## Interface and stage rules

The common contract identifies the stage and adapter version, original request
and schema, indivisible assignments, shared context, output budget, finite call
and depth limits, and dependencies. The executor measures the actual encoded
input including schema, reserves output capacity, persists a plan and each
result, and validates the assembled original contract. Keep input, raw output,
canonical output and decoded memory bounds distinct. Output-size estimates are
planning hypotheses, not guarantees; actual oversized output has a bounded,
recorded decomposition recovery. A fitting request uses a direct path.

Adapters define semantic partitioning, shared context, piece validation, merge
and bridge obligations. Independent records/decisions can be assembled exactly.
Source interpretation and synthesis retain source identities and supported
alternatives. Candidate generation must preserve every supplied unit and all
interpretation dimensions. Criticism preserves candidate/argument namespaces,
explicit premises, attacks, preferences and uncertainties, then checks relations
between pieces before evaluating the complete graph. Review/correction and
comparison retain their original answer, question and comparator identities.
An indivisible common context or global relation that cannot fit remains an
explicit limitation; no truncation, automatic approval by coverage, majority
vote, or independent-graph union can stand in for it.

Existing account/source partitioners, `pack_items`, grouped review and persisted
phase execution should be reused behind the contract. New stage names must be
rejected unless registered, so later code cannot silently bypass the interface.
Native tools require the assembled original candidate/graph and keep their
existing supported/unsupported semantics.

## Validation and evidence

Use `.venv-context` with CPU devices intentionally hidden for product tests;
mission commands use `.venv`. Preserve production state, raw responses and
original request hashes. Stage tests run against copies, with no external calls.

Required coverage: exact-bound and one-over input/output; complete prompt/schema
measurement; unknown stage; oversized atomic context; complete and duplicate
assignment detection; changed source/schema/version refusal; omitted condition,
exception and cross-piece attack; conflicting IDs; failed independent piece;
merge/bridge failure; successful checkpoint reuse; crash with RESERVED response;
finite noncontracting recovery; actual P14 output reproduction; every active
request type and native post-assembly invocation; end-to-end answer and matched
comparison integration. Compare decomposed and direct paths on controlled cases
whose source-grounded consequence is known; do not promote scripted answers as
live legal evidence.

Retain stage inventory, test reports, production replay, source diff, review,
run manifest and adoption transaction under
`artifacts/legal-mission-control/2026-10-20/common-capacity-interface/`.
The run manifest records commit, actual commands/environment, intentional CPU
mode, exact inputs, timings, plan and result. After each checkpoint save its
result, refresh the ready set and continue independent authorized work. Invalid
shared evidence or authority is a continuation veto; a failed stage or service
candidate normally blocks only its consumers. Live deadline expiry blocks live
continuation, not falsely marks integration complete.

## Skeptical pre-execution review

PASS for isolated implementation and no-call validation, conditional on mission
admission. The design addresses the actual output-cap failure and uneven stage
coverage, uses the active route as comparator, and distinguishes capacity from
legal acceptance. Two rejected designs are recorded explicitly: automatically
splitting every JSON array loses semantic relations; raising only the provider
byte bound leaves product token rejection intact. The design instead requires
adapter-specific assembly and one common budget policy at dispatch/validation.
Adoption remains conditional on tested stage coverage and a safely settled
worker; test success alone cannot authorize changed live bindings. Remaining
risks are difficult whole-graph relations, fixed context that cannot contract,
output-estimate error and the unchanged live deadline. Each has a finite
diagnostic and explicit failure disposition above.

## Reviewed implementation decisions

The selected profile is `common-stage-capacity.v1`. Source observations retain
3,000 output tokens / 24,000 raw bytes. Notes, atomic reviews, warrant decisions
and corrections receive 4,096 / 32,768. Candidate generation, criticism, grouped
reviews and matched comparisons receive 8,192 / 65,536. These are bounded
engineering hypotheses, not measured provider capacity. The retained P14
criticism requires 3,909 canonical tokens and 24,273 raw bytes: the 8,192-token
profile provides explicit room for its coupled graph and larger supported
examples. Actual overflow is still checked. Expanded output retains the original
250,000-token / 2,000,000-byte bound. Input grants remain task-specific and unchanged.

Each logical operation allows at most 31 distinct leaves, depth four and four
hours of elapsed time, always subordinate to the global call/deadline checks.
This bound follows a binary tree of depth four; it is a stop condition rather
than a promise that all leaves will fit. Output estimates of 768 tokens per
warrant/source decision and 1,200 per grouped review are conservative planning
hypotheses. Forced actual-overflow controls test the fallback when they are wrong.
Neither a service timeout nor exhausted admission is treated as output overflow.

The four partition adapters are source/metadata record observations, independent
warrant issues, grouped individual reviews, and partial requirement-source
readings. Warrant and grouped-review pieces retain the full shared answer,
sources and adverse context. Their merges preserve every assignment and rebase
assertion or rationale namespaces. Source-note pieces require a joint bridge
with every original source and all partial readings; if that bridge does not
fit, the result remains explicitly incomplete. Existing synthesis/grouping
owners keep their checked contraction logic. Coupled candidates, argument
graphs, answer corrections and matched comparisons are explicitly atomic.
The interface supports them through measured budgets, durable results, and a
precise unsplittable remainder; it does not claim a universal legal decomposer.

All current model calls enter the shared dispatch/phase interface, including
source recovery, correction and comparison sessions. Native retrieval, formal
candidates, argument-graph evaluation and deterministic metadata inventory
receive a complete-input memory check. New unregistered stages fail closed.
Historical sealed routes remain opt-out. Successful common candidate/criticism
results and failures are shared among matched arms under exact request/schema
identity, so another arm cannot buy a new interpretation.

P14's retained size-only failure can be revalidated without a replacement
sample: verify the complete transport manifest, completed turn, absence of
forbidden tool events, exact request/schema/decoder, current size bounds and
original semantic validator. Preserve the original failure and add a separate
revalidation result. Schema failures, semantic rejection and uncertain requests
are ineligible. The local replay preserves all 16 unresolved P14 questions.

## Adoption and continuation

The previous worker owns a scheduled paid replacement. No bound production file
may change until its wrapper has settled and all recorded processes are dead.
If it continues beyond local implementation, a fixed single-use continuation
may wait on its authenticated process identities and result, then take the
master/supervisor locks, freeze exact predecessor files, adopt only the reviewed
diff, register the same graph, refresh and drain authorized ready work. It must
refuse changed staging files, active/uncertain owners, changed predecessor code
or an incomplete deployment transaction. It preserves the service circuit and
its spent replacement budget. Deadline expiry permits local adoption and
verification but vetoes live dispatch; that state must be reported as blocked.

Only failed/interrupted original acquisition, answer/tool and comparison owners
are eligible for one changed-contract continuation. Existing unused attempts are
used first; exhausted owners gain at most one explicitly recorded attempt.
Successful owners, all earlier attempts, completed preparation, legal criteria,
source qualification, service charges and deadline remain unchanged. Substantive
failures remain failures, and no successful answer is resampled for approval.

The retained arm checkpoint includes exact validated answers, individual reviews
and warrant decisions, plus complete native-tool results with their original
evidence paths. Requests and schemas must still match after capacity-only
instruction normalization; a changed successful answer request is refused.
Review populations may grow when a previously blocked group now fits, so review
reuse searches for identical substantive requests as well as their original key.
Semantic failures remain recorded failures. Only missing resource/service work
is eligible for the reviewed continuation. Native-input changes cannot silently
replace retained evidence or change a matched comparator.

The shared-result journal records ownership before transport. If publication is
interrupted, the same owner can reconcile its durable dispatch; another arm is
blocked from resampling. Adoption checks both model and native reservations. Its
process checks must run in the trusted host context: a sandbox can expose a
different `/proc` namespace, so absence there is not evidence that the worker died.

## Implementation review checkpoint

The skeptical implementation review found and repaired four material hazards:
successful calls inside failed arms were not initially carried forward; shared
results had a publication crash window; a new common preparation could have no
legacy dispatch journal; and a continuation result initially hid nonzero local
exit codes. Exact call/native reuse, a pre-dispatch shared owner record, explicit
empty common journals and truthful continuation results address those findings.
Targeted tests exercise each path. Adoption remains conditional on its checked
manifest and predecessor settlement; source qualification and accepted live
answers remain separate product work.

The final regression suite passes 174 tests. A replay through the actual P14
baseline construction preserves all 16 completed calls (the answer, eight
requirement reviews and seven warrants). It exposes 351 previously blocked
source-review requests and divides the one missing warrant into two bounded
pieces; all new responses in this diagnostic are deliberately refused offline.
That is a workload observation, not a source-review success. The remaining live
window may be insufficient to finish it. No call allowance or deadline is enlarged.

The reviewable command-prefix proposal is
`docs/implementation/legal-mission-control/common-capacity.rules`. The deploy
wrapper's exact `arm` command is the single trusted entry for waiting, adoption,
registration, live continuation and local refresh. Repository rule text does not
install itself into protected host settings; use the host's narrow prefix
approval for that command. No broad interpreter or arbitrary-shell approval is
needed.
