# Integration master: bounded execution refresh (14 October 2026)

This is an amendment to `legal-integration-master-2026-10-13.md`, not a new
mission or a replacement for its original 89 tasks. The original four
questions, 46 obligations, 35 readings and 12 cases remain the acceptance
population. The old task outcomes, first and second attempts, 232 current live
charges, 41 separate historical calls, original grant, model/account, call
ceiling and deadlines remain fixed. Current live and legal completion are open.

## Research intent and evidence contract

The question is whether the retained source and implementation can support a
complete, source-warranted original answer and a matched effect assessment for
each selected tool. The comparator is the unchanged original-question baseline
on the same sources, model and review procedure; each tool candidate differs
only by its declared native feedback. Promotion needs an accepted complete
answer, every applicable original inventory item considered, source citations
and contrary passages reviewed, and a valid matched comparison. A wrong
source, missing exception, unbound code, exhausted authority or failed
fresh review vetoes promotion. Local quote matches, native adapter passes,
request-size checks, and service canaries are explanatory or prerequisite
diagnostics, not legal or matched-effect promotion criteria. A passing synthetic
semantic control proves only that scoped control. The result is retained in
the existing master state, individual package receipts, mission history and
this amendment's result note.

## Skeptical pre-execution audit

The master currently has no ready task: 23 succeeded, 10 blocked, four failed
historical acquisitions and 52 dependency-blocked. This is a scheduling fact,
not a legal verdict. The old local `qualify-*` results have no successful live
semantics, and the `campaign` and `live-approval` owners are blocked. The four
`acquire-*` owners have three recorded attempts each; none may be reset or
renamed to evade that limit. A proposal measured 13,429 worst-case calls against
7,868 then remaining, so all arms cannot be promised under that conservative
bound. Staged actual-population budgeting is required. Transport 502/503 and
timeout outcomes do not prove a semantic failure. The current provider check
binds archived implementation paths; merely deleting the `live()` revision
guard would be unsafe. The preflight must bind current code, source and provider
without requiring its own success first. The old local source work retains
answer-relevant passages but has not qualified full judgment numbering or
all Handbook clause boundaries. This does not stop independent conditional
inventory analysis.

The inherited two-reader design, cl100k local token estimates, six native
adapters, model route and fixed request bounds are hypotheses or approved
resources, not proof of correctness. Early diagnostics are exact source hash,
provider-visible request measurement, current code identity, scoped semantic
controls, and original item-by-item source checks. Full downstream answer
review remains necessary. No result may silently turn a local pass into legal
fulfillment.

   Preserve every earlier result in its immutable attempt. Validate the
   old program against archived bytes, then validate the extension, attempt
   ceiling and unchanged resource limits. Local capacity success is separated
   from semantic success: acquisition requires both. The registration itself is one
   reviewed consolidated detour, not a fresh historical budget.
2. Four independent `inventory-QUESTION` branches read the current retained
   source envelope, the corresponding successful conditional account and all
   original items assigned to the question. For each reading, check every
   quoted passage against the exact source unit; for every challenge obligation,
   retain its unresolved premises; for each case, retain the actual facts and
   rejection. Produce an item-by-item conditional review and exact blockers.
   A failed question does not block the other three. These are review receipts,
   not complete live answer fulfillment.
3. Independently inspect the current preflight binding. Bind the current
   source, implementation, provider route, ledger and grant to a finite
   proposal, retaining exact historical archives. Do not dispatch before the
   proposal and a focused identity test pass. A failed binding blocks only
   live consumers. Keep source/legal branches schedulable.
4. Run one current actual-product remote/changed-exception preflight under
   the existing grant only when the current binding is verified and remaining
   calls and time admit the finite stage. Retain all calls and both outcomes.
   Service failure is an inconclusive transport result. A substantive failure
   blocks its consumers and triggers one reviewed implementation repair, not
   a blind redispatch. A pass permits question-specific service canaries and
   acquisition admission; it does not accept an original legal answer.
   The semantic-preflight node has one finite execution with at most 128 calls.
   It is separate from acquisition so a failed preflight consumes no acquisition
   attempt. The existing four acquisition owners are reviewed here for exactly
   one fourth attempt, conditional on that preflight and their own canaries.
   They are not silently renewed if the semantic control fails.
5. Admit original acquisition only after its own source, capacity, semantic
   and canary prerequisites. Any fourth attempt must be explicitly reviewed
   against the three historical attempts and the unchanged call grant. Budget
   generated populations and correction reserves by stage. Baseline and tool
   branches for one qualified question are independent of other questions;
   comparison requires both the baseline and candidate. Finish by assessing
   actual answers and matched effects, or retain exact unresolved owners.

After **each** completed local or live package, persist its result, append the
mission history and next-task reason, and execute
`.venv/bin/python scripts/legal_mission_control.py refresh`. The existing
`Execution.finish`/`MasterExecution.sync_mission` already does this for
scheduler packages; the runner drains other ready branches after a failure.
When a repair is needed, name the failed node, diagnosis, affected consumers,
one finite attempt and return path before editing. Stop a consumer for corrupt
evidence, changed code or source without archive, uncertain in-flight call,
expired authority, exhausted reviewed calls, or a failed required semantic
control. Continue every independent source/legal branch.
