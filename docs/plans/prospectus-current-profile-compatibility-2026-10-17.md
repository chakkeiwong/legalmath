## Limits and decisions

The first proposal is one reviewed native-binding admission, 20 to 21. Its
execution envelope remains nine stages, 720 recorded stage seconds and 32 MiB
of new evidence, with one focused test start, zero new native/subprocess calls,
115 seconds per stage and a 195-second independent checker under a 210-second
outer record limit. All prior resource usage is retained and reported before
admission; the new envelope is an explicit addition, not a reset. Every start
is exclusive and an interrupted/failed stage cannot be repeated unchanged.

Later task admissions are conditional, not automatic allowances: installed
11 to 12, recovery 15 to 16 and authority 7 to 8 each require the existing
`revise` operation with a full original admission list and the actual result
of its predecessor. Installed current capture/lifecycle is not covered by the
native phase and may require four actual native source calls. Before any such
calls, the installed review must bind the exact current wheel target, existing
runtime, source documents, full per-route requests, process reservations,
storage/workspace forecasts and failure reserve. No unchanged profile is
re-pinned as current. Recovery must separately address the original isolated
workspace overrun without weakening its eight-state target. No changed shared
method may silently invalidate a completed phase; if that happens, repair the
design before spending more.

Changed source or historical evidence, an unreviewed method/package delta,
missing route/state/control, unequal complete products, a wrong refusal,
checkout leakage, unexpected process/network action or exceeded resource bound
vetoes the affected candidate. A known absent independent source or reader
vetoes delivery, but does not veto this finite engineering investigation.
Timing, file totals and test counts are explanatory/resource diagnostics.

No result here establishes new source authenticity, accounting compliance,
controlling incorporation, independent legal acceptance, portability, general
table extraction, all-tool integration or transaction entitlement. Shared
interpretation errors can survive all current-versus-retained comparisons.

Commands use one stage per invocation, normally
`timeout 120 .venv/bin/python -m scripts.prospectus_profile_delta_runner
--attempt <admitted-path> --stage <stage>` for the native phase. Tool yields
are one second and the same session is polled to actual exit. Retain actual
commands, commit, interpreter, CPU-only setting, source/method hashes, elapsed
time, result and decision in the admitted attempt. Record, refresh and inspect
the real state after each phase. Checkpoints do not end execution.

## Defaults, assumptions and skeptical design review

The original five native routes and eight recovery states are the accepted
denominators, not convenient subsets. The source09/014 normal wheel is an
exact current package comparator, not a financial oracle. Old statement-cell
profiles remain exact; additions do not authorize arbitrary future profile or
function changes. AST checks supplement exact before/after hashes and actual
downstream comparisons. The original 115/720/195-second native limits are
retained hypotheses supported by native020's 236.15-second staged execution;
unexpected overhead is a recorded failure, not grounds for silently extending
the clock. CPU-only commands set `CUDA_VISIBLE_DEVICES=-1` before imports.

Skeptical design audit: PASS for the bounded first phase, with later phases
requiring the stated implementation/resource reviews. The audit rejected four
shortcuts: treating the capital profile's four controls as all native routes;
calling the 434-file installation current; changing a global acceptance module
and thereby invalidating every task; and rehashing old source execution records
as new executions. Exact delta review, complete original denominators, a stable
native-specific isolated dispatch and unchanged core validators address those defects. Current
installed-path compatibility and recovery workspace growth are explicit early
diagnostics, not hidden assumptions.

The strongest misleading-pass risk is a shared semantic error in old and new
products. A changed full answer, wrong source position or accepted adverse case
would overturn compatibility. The strongest false-failure risks are stale
helper paths, wrong package roots and copying irrelevant history into the
recovery workspace. Inspect those before admitting their phases. A failed
candidate triggers a bounded diagnosis at the failing layer; it does not by
itself reject the package or the prospectus approach.
