The controller records the following sequence for the same target question:
1. two extraction methods inspect the retained circular and source anchors are checked
against its text; absent authority text remains absent;
2. the breadth scheduler retains every imported reading and its assumptions, with
archived origin explicitly distinguished from fresh generation;
3. an argument graph records the support for each family and the absence of a retained
authority deciding the disputed connection;
4. RuleIR type checking checks each restricted encoding;
5. a finite solver query finds a permitted input on which the two encodings differ, and
the witness is replayed in the actual Python and Java evaluators;
6. the Java artifact is bound to the exact RuleIR bundle and snapshot set; and
7. the installed pinned Catala backend is compiled and replayed over the same de-
clared cases; missing tools or unsupported operations are recorded as such, and
the disabled live provider supplies no fresh evidence.
The result is therefore a useful but blocked dossier. Its formal and execution checks can
succeed for their declared cases, while the authority question remains open. The host
receives an unresolved result and the smallest question that could change it. It does not
receive an approval.
6.34.3 Why a formal proof is valuable and still insuﬀicient
The proof layer is most useful when its proposition is explicit. A Lean proof, an SMT
unsatisfiability result or a checked Java/JML property can establish a statement such as
∀x ∈D :
EPython(x) = EJava(x),
(6.11)
where D is the declared finite or symbolic input domain and both evaluators have the
same fact vocabulary, time semantics and result categories. A proof of (6.11) is evidence
about translation and execution. It is not a proof that the source intended the predicate
E.
